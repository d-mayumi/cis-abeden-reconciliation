# CIS・あべでん料金突合システム AI技術検証報告

| 項目 | 内容 |
|---|---|
| 検証日 | 2026年8月17日 |
| 対象 | CIS①・CIS②・あべでんの帳票読取、Google Sheets連携、料金突合処理 |
| 検証方法 | ソースコード監査、自動テスト、型チェック、本番ビルド、OpenAI公式仕様との照合 |
| 総合判定 | **条件付きPoC合格／本番投入は保留** |

## 1. 結論

通常の料金突合ロジックと、AI読取結果を所定のスプレッドシートへ連携する処理フローは、自動テスト・型チェック・本番ビルドを通過した。

一方、AI/OCR部分はテスト内でOpenAIの応答を固定値に置き換えており、実際のCIS・あべでん帳票に対する読取精度は測定されていない。また、現在はAIが1行以上を返すと、重要項目が空欄でも人手確認なしでGoogle Sheetsへ追記される。

したがって、現時点で正確に言えるのは次の範囲である。

> **AI/OCR連携の処理フローは検証済み。認識精度と安全な登録運用は、正解付き実帳票による追加評価と実装修正が必要。**

本番利用の前に、正解付き帳票評価、人手確認画面、厳格な出力検証、二重登録防止、データ保持設定の5点を必須対応とする。

## 2. 判定一覧

| 検証領域 | 判定 | 根拠 |
|---|---|---|
| 料金突合ロジック | 合格 | 需要家ID・対象年月・名称・金額・重複データ等の自動テストが成功 |
| AI連携の処理フロー | 条件付き合格 | PDF入力、JSON受領、保存先振分、Sheets追記までの契約テストが成功 |

| AI/OCR認識精度 | 未評価 | 実帳票と正解データを用いた評価が存在しない |
| 登録前の業務統制 | 不合格 | AI出力を確認・修正せず即時追記する |
| 個人・取引データ保護 | 要改善 | OpenAIへの送信は行うが、保存抑止設定と運用合意が未整備 |
| 障害復旧・二重登録防止 | 要改善 | タイムアウト、再試行、冪等性、永続監査ログが不足 |
| 本番投入可否 | 保留 | 上記の必須対応と実帳票評価の完了後に再判定 |

## 3. 対象システムのAI処理

1. 利用者がCIS①、CIS②、あべでんのいずれかを選択し、帳票をアップロードする。
2. サーバーが帳票と抽出指示をOpenAI Responses APIへ送る。
3. AIが「対象年月、需要家ID、需要家名、請求金額、発行日、元ファイル名」の6項目をJSONで返す。
4. サーバーが文字列へ整形し、選択された固定のGoogle Sheetsタブへ追記する。
5. 保存した6列データを画面から再読込し、確認する。

通常の料金突合はこの経路とは別に、CSV・Excelファイルをブラウザで読み込み、227列の入力データを処理して236列の結果を出力する。OCRの6列データから通常突合へ自動接続する処理は、本コード内には実装されていない。このため、現状のAI機能は「帳票から一覧表を作るPoC」であり、「AI読取から料金突合完了までの一貫自動化」ではない。

主な実装箇所は、[モデル設定](../api/ocr.ts#L5)、[抽出指示](../api/ocr.ts#L85)、[OpenAI呼び出し](../api/ocr.ts#L121)、[Sheets追記](../api/ocr.ts#L147)である。

### 4.2 OpenAI公式仕様との照合

PDFをBase64データとして `input_file` へ渡す方式は、Responses APIの公式なファイル入力方法に沿っている。PDFでは抽出テキストとページ画像の両方がモデルへ渡される。[OpenAI File inputs](https://developers.openai.com/api/docs/guides/file-inputs)

一方、次の差分がある。

- 画面は画像ファイルも受け付けるが、サーバーは画像も `input_file` として送信する。画像入力の公式方式は `input_image` であり、画像経路は修正と実機確認が必要。[OpenAI Images and vision](https://developers.openai.com/api/docs/guides/images-vision)
- 現在はJSONオブジェクト形式の指定のみで、項目の型・必須条件を厳格に保証していない。JSON Schemaを使うStructured Outputsへ移行し、拒否応答や不完全応答も明示的に扱うべきである。[OpenAI Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs)
- `store: false` が指定されていない。APIデータは既定では学習に使われない一方、Responses APIの応答状態や不正利用監視ログには保持期間があるため、保存抑止設定と社内のデータ取扱方針を揃える必要がある。[OpenAI Data controls](https://developers.openai.com/api/docs/guides/your-data)
- PDFの表示詳細度を指定していない。小さい文字や罫線を含む請求書では、精度・トークン量・費用を比較したうえで表示詳細度を決める必要がある。

## 5. 主要リスクと必須対応

| 優先度 | リスク | 現状と影響 | 必須対応 |
|---|---|---|---|
| P0 | AI精度が未測定 | テストはAI応答を固定値で再現しており、欠落行・架空行・誤読を検知できない | 正解付き代表帳票を作り、行数と重要項目の完全一致を測定する |
| P0 | AI読取と料金突合が未接続 | 6列のOCR保存経路と227/236列の通常突合経路が別で、システム内の一貫処理になっていない | 入出力契約と責任境界を確定し、変換・検証・突合までの通し試験を追加する |
| P0 | 未確認データの自動登録 | 抽出行が1件以上なら、ID・年月・金額が空欄でも即時追記される | 「抽出→検証→利用者確認→登録」の4段階に分ける |
| P0 | データ保持条件が未確定 | 需要家名、需要家ID、請求金額を外部APIへ送信する | `store: false`、送信可否、保持期間、契約条件、利用者への告知を確定する |
| P0 | 二重登録の可能性 | 画面内の重複抑止のみで、再読込・通信再試行・別端末には効かない | ファイルハッシュ、保存先、帳票識別子によるサーバー側冪等性を実装する |
| P1 | 出力検証が弱い | AIの値をほぼ文字列化するだけで、年月・ID・金額の形式や範囲を検査しない | 厳格なJSON Schemaと業務ルール検証を追加し、不正値は登録しない |
| P1 | 画像入力方式の不整合 | 画面仕様とOpenAIへの送信形式が一致していない | 画像は `input_image`、PDF等は `input_file` に分岐する |
| P1 | 障害対応不足 | タイムアウト、429/5xx再試行、出力上限、部分失敗処理がない | タイムアウト、指数バックオフ、再試行上限、処理単位の状態管理を実装する |
| P1 | 監査証跡不足 | OCRログは画面を閉じると消え、モデル版・要求ID・所要時間・費用を追えない | 内容を過剰保存せず、帳票ハッシュ、モデル版、要求ID、件数、所要時間、結果を永続記録する |
| P1 | モデル変更時の回帰リスク | `gpt-4.1-mini` の移動エイリアスを使用している | 検証済みスナップショットを固定し、変更時は同じ評価セットで回帰試験する |
| P1 | ファイル解析ライブラリの既知脆弱性 | `xlsx` に高、`uuid` 経由に中の指摘があり、未信頼のExcel入力を処理する | 修正版または代替ライブラリへ移行し、移行まで容量・時間制限と隔離を行う |
| P1 | 通常書込APIの入力検証不足 | 固定シート以外は拒否するが、236列・行数・型・書式範囲をサーバーで再検証しない | サーバー側で許可するデータ形と書式を再構築し、部分成功を明示する |
| P1 | 変更追跡・復旧証跡の不足 | 対象フォルダは専用Git履歴を持たず、上位リポジトリもコミット0件のため差分レビューと復旧の基準点がない | 専用リポジトリまたは管理対象として初回基準版を記録し、レビュー・リリース手順を整備する |
| P2 | 画面配信容量 | JavaScriptがgzip後500 kBを超える | 遅延読込と分割で初期表示容量を削減する |

補足として、Basic認証は設定不足時に拒否する設計だが、READMEの本番環境変数一覧にはBasic認証とSupabaseログ用の設定が十分に記載されていない。導入手順と実装の差分を解消する必要がある。

依存ライブラリの監査根拠は、`xlsx` の[Prototype Pollution](https://github.com/advisories/GHSA-4r6h-8v6p-xvw6)・[ReDoS](https://github.com/advisories/GHSA-5pgg-2g8v-p4x9)と、`uuid` の[境界検査不備](https://github.com/advisories/GHSA-w5hq-g745-h8pq)である。`xlsx` は監査時点で自動修正版が提示されていないため、ライブラリ選定を含む対応が必要となる。

## 6. AI品質の提案合格基準

本番判定には、CIS①・CIS②・あべでんを各10帳票以上、合計30帳票以上の正解付き評価セットを用いる。通常帳票だけでなく、複数ページ、傾き、低解像度、薄い印字、罫線崩れを含める。

| 指標 | 提案合格基準 |
|---|---|
| 帳票内の行数 | 全帳票で完全一致 |
| 需要家ID | 100%完全一致 |
| 対象年月 | 100%完全一致 |
| 請求金額 | 100%完全一致 |
| 欠落行・架空行 | 0件 |
| 誤った保存先 | 0件 |
| 二重登録 | 0件 |
| 読取不能時 | 自動登録せず、理由を示して人手確認へ移行 |
| モデル更新 | 同一評価セットで上記基準を再達成 |

請求業務では1件の誤登録も後工程へ影響するため、平均正解率だけで合格にせず、重要項目は完全一致を要求する。完全一致しない帳票を扱う場合は、人手確認を必須にする。

## 7. 推奨実施順

### 本番投入前（P0）

1. 正解付き帳票30件以上と自動評価プログラムを作る。
2. OCRの6列データから料金突合までの入出力契約を確定し、一貫処理を実装する。
3. 登録前プレビュー、修正、承認画面を追加する。
4. 重要項目の必須・形式・範囲チェックとStructured Outputsを実装する。
5. `store: false` とデータ取扱ルールを適用する。
6. サーバー側の二重登録防止を実装する。
7. 画像入力を公式形式へ修正し、PDF・画像の双方を実帳票で確認する。

### 試験運用前（P1）

1. タイムアウト、再試行、部分失敗、件数・容量上限を実装する。
2. モデル版、帳票ハッシュ、件数、要求ID、所要時間、結果の監査ログを残す。
3. 検証済みモデル版を固定し、費用・処理時間も評価する。
4. OpenAI、Google Sheets、Supabaseを接続したステージング通し試験を行う。
5. READMEの環境変数、ファイル数、対応形式を実装と一致させる。
6. `xlsx` 等の既知脆弱性を解消し、通常書込APIの入力をサーバー側で検証する。

### 継続改善（P2）

1. 読取困難帳票の傾向を集計し、確認対象の判定ルールを改善する。
2. 画面のJavaScript分割と遅延読込を行う。
3. モデル、プロンプト、帳票様式の変更を評価セットで継続監視する。

## 8. 今回実施していない検証

- 実際の顧客帳票をOpenAIへ送信する認識精度試験
- OpenAI、Google Sheets、Supabaseへの本番接続試験
- ブラウザを用いた実環境E2E試験
- 負荷試験、大容量・大量ファイル試験
- 障害注入、通信切断、レート制限時の復旧試験
- セキュリティ侵入試験および外部の法務・個人情報保護レビュー

今回の監査では顧客帳票や機密データを外部へ送信していない。上記未実施項目を完了し、P0項目を解消した時点で本番可否を再判定する。

## 9. 最終所見

本システムは、保存先の固定、誤タブへのフォールバック防止、料金突合の決定的ロジックなど、業務事故を避ける基礎は備えている。一方、AIが返した結果を正しいと仮定して即時登録する構造が、現段階の最大リスクである。

AIは「自動確定者」ではなく「入力候補の作成者」として扱い、業務ルール検証と利用者確認を通過したデータだけを書き込む構成に変更することで、試験運用へ進められる。
